# Five steps: closing the verification gaps (v41)

Every previous round ended with the same caveat — *"the SQL is unverified, the types are
unverified"*. These five steps close as much of that as is possible without an Android
toolchain, and state precisely what is left.

## 1. Room SQL validated against a real SQLite engine

`scripts/verify-sql.py` derives a schema from the `@Entity` declarations the way Room
does, then **prepares all 42 `@Query` strings** against SQLite. Preparation resolves table
and column names and parses the syntax without needing data.

Confirmed to work by breaking it: renaming a column to `folderNam` produced
`no such column: folderNam`.

## 2. Migration chain executed and diffed against the entities

A bad migration is the worst thing this app can ship: it passes review and fresh installs,
then crashes *existing users* at launch after an update. `scripts/verify-migrations.py`
replays all 22 `execSQL` statements from a pinned v1 schema through v5, then diffs the
resulting tables against the `@Entity` declarations.

**The first version of this check was worthless, and I caught it by testing it.** It
reconstructed v1 as "entity columns minus those a migration adds", so a newly added column
with no migration was silently absorbed into v1 and never reported — the exact case the
check exists for. Adding such a column and watching it pass proved the flaw. v1 is now
pinned as a literal, documented as history that must never be edited to make a check go
green. Re-tested:

```
photos.newlyAddedColumn exists on the entity but no migration adds it
    -- an upgrading install would crash
```

## 3. A documented assumption of mine turned out to be false

I had written, in code comments and in two notes files, that SQLite cannot parse `IN ()`,
and built a sentinel-padding workaround on that basis. Testing it directly:

```
empty IN () accepted -- would NOT be caught
```

**SQLite accepts it.** The workaround is harmless and still worth keeping — `IN ()` is a
SQLite extension rather than standard SQL, and not depending on Room's empty-collection
behaviour is defensible — but the stated reason was wrong. Both comment sites now say
what is actually true. The behaviour was fine; the explanation was fiction.

## 4. Settings model brought into the type check

`AppSettings`, `CredentialPolicy` and the weather model now type-check against stubbed
`kotlinx.serialization` annotations.

`ConfigTransfer` and `PortableBundle` are **deliberately excluded**. They call
`.serializer()` functions generated by the serialization compiler plugin, which runtime
stubs cannot model. The resulting errors were artifacts of my stubs, not defects in the
code — and the right response was to exclude the files, not to reshape working code to
satisfy a fake dependency.

The full `SlideshowViewModel` was attempted and abandoned for the same reason: its Android
surface is tiny (`Context`, `Uri`, `ViewModel`, `viewModelScope`), but its transitive
closure runs through ServiceLocator into Room, Coil, NanoHTTPD and DataStore. Stubbing
that far produces noise rather than signal.

## 5. Documentation reconciled

`README.md` now describes multi-source pools and folder selection, and carries an accurate
account of what the offline gate does and does not cover. `KNOWN_LIMITATIONS.md` gains a
verification-status section that corrects earlier over- and under-statements.
`CAPABILITIES.md` — machine-verified, 25 rows — now includes the three new harnesses.

## Where this leaves the project

**Now verified:** all Room SQL parses against SQLite; the migration chain executes and
matches the entities; the engine, DAO, indexer and settings model type-check; the pure
decision logic executes.

**Still unverified:** the whole UI/ViewModel layer (parse-only, and holding the largest
untyped refactor); Room's generated code and schema hash; `ConfigTransfer` /
`PortableBundle` types; and everything about runtime behaviour on a device or against a
real NAS.

Every check added here was deliberately broken once to confirm it fails — after the
migration check taught me that an untested check can be confidently wrong.

`./gradlew --no-configuration-cache clean testDebugUnitTest assembleDebug` remains the
gate that matters, and now has much less left to discover.
