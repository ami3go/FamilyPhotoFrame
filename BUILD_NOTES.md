# Build Notes — architecture and release decisions

This records the decisions a reviewer would otherwise have to reverse-engineer,
per spec §28 Definition-of-Done and §3.1/§3.2.

## SDK levels

| Setting | Value | Why |
|---|---|---|
| `minSdk` | 21 (Android 5.0) | Product requirement for older wall-frame hardware; guarded and desugared APIs are required. |
| `compileSdk` | 35 | Build against the latest stable platform. |
| `targetSdk` | 35 | Opt into current runtime behavior; required for Play. |

`java.time` is used on API 21–25 via **core library desugaring**
(`isCoreLibraryDesugaringEnabled = true`, `desugar_jdk_libs 2.1.2`).

## Pinned versions

Every version lives in `gradle/libs.versions.toml`. No dynamic versions, no `+`
ranges (Contract Rule 9). Notable pins: AGP 8.5.2, Kotlin 2.0.21 (with the
separate `kotlin-compose` plugin, which is how Compose is enabled from Kotlin 2.0),
KSP 2.0.21-1.0.28, Compose BOM 2024.09.03, Room 2.6.1, Coil 2.7.0,
kotlinx-serialization-json 1.7.3, coroutines 1.9.0.

## Image loader: **Coil**, not Glide

The spec allows Coil **or** Glide. Coil was chosen because:

- It is Kotlin-first with first-class Jetpack Compose support
  (`rememberAsyncImagePainter`, `AsyncImage`), so the slideshow stays idiomatic
  Compose with no `AndroidView` bridging.
- It accepts `content://` `Uri` and `File` models directly, which matches the two
  Phase 0 sources (SAF documents and app-private files) with no custom loader.
- Coroutine-native cancellation aligns with the engine's structured concurrency.

Crossfade is handled by the Compose `Crossfade` composable (duration from settings)
rather than Coil's built-in crossfade, so the engine's current/next model drives
exactly one transition and we never hold more than two decoded bitmaps (spec §10.2).

## Config storage: typed DataStore (JSON), not Proto DataStore

The spec suggests Proto DataStore. We use a **typed `DataStore<AppSettings>`** with a
`kotlinx.serialization` JSON serializer instead. Rationale:

- It yields a single, strongly-typed runtime config object (`AppSettings`), which is
  exactly the property the spec wants ("avoid an ambiguous DataStore-vs-JSON runtime
  split") — without pulling in protobuf codegen for a Phase 0 spike.
- The **same** `Json` format is reused for the import/export feature later, so there
  is one schema, one `schemaVersion`, one place to evolve.
- On a corrupt file the serializer throws `CorruptionException` and a
  `ReplaceFileCorruptionHandler` restores defaults — the app never crashes on bad
  config (Contract Rule 1).

If a future phase needs Proto's stricter schema/codegen, the serializer is the only
class that changes; `SettingsRepository` and all callers are unaffected.

## Database & migrations

Room currently uses **schema version 5**, exports schema metadata, and has explicit additive
migrations `1→2→3→4→5`. `fallbackToDestructiveMigration()` is deliberately not used.
`verify-sql.py` prepares all current DAO queries against SQLite and `verify-migrations.py`
replays the complete migration chain before each packaged delivery.

Identity is `(sourceId, normalizedPath)` via a **unique index**; a surrogate
autogenerated `id` is the primary key, so a rescan of a changed file updates the same
logical row (REPLACE on the unique index) instead of duplicating it.

## Concurrency / threading

No disk or network I/O on the main thread (Contract Rule 2). Every source, Room,
and settings call is `suspend` and runs off-main via `AppDispatchers` (an indirection
so nothing hard-codes `Dispatchers.IO`). **StrictMode** is installed in debug
(`App.kt`) with `penaltyLog` for disk/network on main and leaked closables — the
Phase 0 acceptance run asserts no violations.

## The slideshow engine

A single command-driven coroutine owns timing and the current/next photo
(`SlideshowEngine`). Auto-advance is a `withTimeoutOrNull(interval) { commands.receive() }`
so a D-pad/web command **pre-empts** the wait instead of fighting a separate timer.
Selection reads a least-recently-shown **window** from Room and applies
`least_recent_random` (spec §9.6 MVP mode). The engine never enumerates storage.

## Scanning / indexing

`SafPhotoSource` traverses with `DocumentsContract` child-document queries and an
explicit work-stack rather than `DocumentFile.listFiles()`, which allocates an object
per node and is too slow on large trees (spec §7.11). The scan emits a
`Flow<ScanEvent>` (never a `List`), and `Indexer` inserts in batches of 200 and then
reconciles by deleting rows not refreshed by the latest scan (Contract Rule 3,
unbounded-list prohibition).

## Permission audit task

`app/build.gradle.kts` registers a `PermissionAuditTask` per variant that reads the
**final merged manifest** (`SingleArtifact.MERGED_MANIFEST`), fails the build if any
of eight forbidden broad media/storage permissions is present, and writes a report to
`build/reports/permissions/<variant>.txt`. It is wired as a dependency of
`assemble<Variant>`, so a normal build can't skip it (spec §7.8, §21.4, §27.8/§27.9).

## Release build

Release builds enable R8 and resource shrinking. A configured production keystore is used when
available; otherwise the current build deliberately emits a prominent warning and falls back to
the debug key for private testing. A debug-signed release must never be distributed. Public
release hardening must change this fallback to a fail-closed production-signing gate.

## Deferred work

Current deliberate deferrals include encrypted browser transport, resumable/chunked web upload,
HEIC conversion on Android 5/6, optional writable-SAF upload destination, production signing
fail-closed behaviour, and full API 21/API 36/public-store validation.

## minSdk 21 (Android 5.0) — deviation from spec §2

Spec §2 sets the commercial floor at **minSdk 24** and says API 21 must not be
supported "until separately validated". This build lowers the floor to **21** by
product decision, to run on older hardware. Recorded here because it is a deliberate
deviation, not an oversight.

**What it changes in code.** Only one thing actually breaks below API 23:
AndroidKeyStore cannot hold *symmetric* keys before Android 6, and
`KeyGenParameterSpec` / `KeyInfo` do not exist there. `KeystoreSecretStore` therefore
branches on `Build.VERSION.SDK_INT`:

| API level | SMB password storage |
|---|---|
| 23+ | AES-256-GCM key generated **inside** AndroidKeyStore, non-exportable. Only ciphertext + IV persisted. |
| 21–22 | Random AES-256 key encrypts the secret; that key is then **wrapped with a non-exportable RSA key held in AndroidKeyStore**. Wrapped key + ciphertext + IV persisted; the bare AES key never touches disk. |

Contract Rule 5 (no plaintext secrets) holds in both modes. The stored `wrappedKey`
column selects the unwrap path on read, so a database written on one Android version
still decrypts on another where the key material allows it; where it cannot, the
source is marked `needs_credential` rather than failing fatally (spec §18.3).

**Schema.** This added `secrets.wrappedKey` (nullable BLOB) → database **v3** via the
additive `MIGRATION_2_3`. No destructive migration (Contract Rule 10).

**Everything else already supported 21**: Compose, Room, DataStore, Coil, SAF
(`ACTION_OPEN_DOCUMENT_TREE` is API 21+), the boot receiver, and NanoHTTPD. `java.time`
is covered by core-library desugaring, which was already enabled.

**What is NOT proven.** See KNOWN_LIMITATIONS.md — API 21–23 is an unvalidated tier.


## Offline verification (`scripts/verify-pure-logic.sh`)

A full `./gradlew` build needs `services.gradle.org` (the wrapper distribution) and
`dl.google.com` (the Android Gradle Plugin and SDK artifacts). Where those are blocked,
the project cannot be built at all — which had left several increments delivered without
ever being compiled.

The Kotlin compiler *is* reachable from GitHub releases, which makes partial verification
possible offline. `scripts/verify-pure-logic.sh`:

1. Downloads kotlinc (version pinned to match `gradle/libs.versions.toml`) and parses
   every file under `app/src/main/java`, failing on genuine **parse errors**.
2. Lifts the pure-Kotlin `ExifParsing` object out of `ExifExtractor.kt` and **runs** it
   against real assertions (`scripts/verify/PureChecks.kt`) — date parsing, caption
   cleaning, GPS formatting, and the locale-independence regression guard.

**What it does and does not prove.** Without the Android/Compose/Room/coroutines
classpath, every reference into those libraries is unresolved, so type errors there are
invisible and the compiler's "unresolved reference", "overrides nothing" and "suspension
functions can only be called within coroutine body" output is expected noise — it appears
in long-standing untouched files too. Treat a pass as "the syntax is valid and the pure
logic is correct", not "it builds". Run a real Gradle build before shipping.

`scripts/check-consistency.py` runs first and covers a third category, invisible to both
a parse check and a pure-logic test, and easy to break silently when editing many files:

  - `R.string` / `R.array` references with no matching resource, and duplicate resource
    names — both compile errors;
  - `vm::foo` callbacks naming a function the ViewModel does not have — a compile error;
  - a Room entity column with no corresponding migration, or a gap in the migration
    chain — **not** a compile error, but a crash on launch for any upgrading install,
    which is the worst place to find it.

Each of those four cases was validated by deliberately introducing it and confirming the
checker fails, so it is not a check that only ever prints "pass".

Current status: consistency checks pass (db v5, migrations 1→5 contiguous); no parse
errors across all main sources; 100/100 pure-logic checks pass.


## Release signing and R8 (added with the release-hardening pass)

`assembleRelease` now runs **R8 with resource shrinking** and signs with a **real
release key** when one is configured. Nothing secret is committed.

Provide the key either with a git-ignored `keystore.properties` at the repo root:

```properties
storeFile=/absolute/path/to/release.jks
storePassword=...
keyAlias=familyphotoframe
keyPassword=...
```

or with environment variables, which is what CI should use:

```bash
export FPF_KEYSTORE=/path/to/release.jks
export FPF_KEYSTORE_PASSWORD=...
export FPF_KEY_ALIAS=familyphotoframe
export FPF_KEY_PASSWORD=...
```

With neither present the release build still succeeds but falls back to the **debug**
key and logs a warning. This is for private testing only. Public release CI must fail when
production signing material is absent.

`enableV1Signing` is on deliberately: this app supports `minSdk 21`, and APK Signature
Scheme v2 alone is not honoured below API 24.

### First run of a minified build is a test, not a formality

R8 has never run on this project. The keep rules in `app/proguard-rules.pro` are
reasoned from which layers use reflection (Room, kotlinx.serialization, jcifs-ng,
NanoHTTPD, Coil, Compose), but reasoning is not verification. Before trusting a release
APK, exercise **on the minified build**: settings load and save, config export/import,
the encrypted bundle round-trip, each configured source type, and the web panel. A
missing keep rule typically shows up as a serialization or `valueOf` failure at
runtime, not as a build error.
